# 消息优先级与控制指令（MESSAGE-PRIORITY）

> 状态：**设计 + 0.1.x 实现**
> 触发：主人 2026-11-07 指出「消息应该有优先级；有些任务 follow 到任务后面，有些要插到所有任务之前；高优先级任务（比如『立即停止』）现在停不了」
> 关联：[COLLABORATION.md](COLLABORATION.md)（投递缺口）、[GROUP-GOAL.md](GROUP-GOAL.md)（目标与约定）

---

## 一、痛点：今天两次真实翻车

### 1.1 停止指令发出去了，然后谁也动不了

```
#603  转达主人「全部停止讨论，排队消息也停止处理」
#625  征集方案意见        → 无人回
#626  再发要点 + 5 问题    → 无人回
#628  固化结论 + 3 问题    → 无人回
#629  第二轮评审 + 真人    → 无人回
```

**只有赵雷 #627 自己回了一条。** 其余四位把 #603 当成持续有效的封口令。

根因不是「他们不配合」，是**「停止」不是一个有状态的东西**：
- 它是普通消息，和其他消息排在同一个队列里
- 它没有解除方式，靠发起人记得去解除
- 发起人（我）忘了解除，于是暂停静默变成了永久

### 1.2 反过来也一样：普通消息压不住正在跑的 turn

一条「立刻停下，线上出事了」和一条「顺便说一句」，在投递层**完全等价**。都排在目标 Session 的下一个 turn。

## 二、现状：能力在，通路没接

`lib/dsh/deliver.js` 已经实现了三种投递模式：

| 模式 | 语义 | 底层调用 |
|---|---|---|
| `followup` | 排到下一个 turn（默认） | `agent.followup(...)` |
| `steer` | **插入正在运行的 turn** | `agent.steer(...)` |
| `inbox` | 只进收件箱，不唤醒 | （不投递） |

**问题在两处：**

1. **发送方无法声明优先级。** `defaultMode` 来自接收方配置（`config.delivery.defaultMode`），一条紧急消息和一条闲聊走同一条路。
2. **群消息根本没接这条通路。** `group/post` 只往 feed 里追加，唤醒与否由订阅/查询决定，没有 mode 选择。

**结论：不需要新造投递能力，需要把「优先级」变成消息的属性，并接到已有的 `steer` 上。**

## 三、设计

### 3.1 三级优先级

```js
entry.priority = 'normal' | 'urgent' | 'control'
// 缺省不写（undefined）——未使用该能力的群、未声明优先级的消息，
// 存储与返回与 0.1.25 逐字节一致，与组织层同一条红线。
```

| 级别 | 语义 | 谁可以发 | 投递 |
|---|---|---|---|
| `normal`（缺省） | 普通发言 | 任何成员 | `followup`（排到下一 turn） |
| `urgent` | 插队，别等我这轮做完 | 任何成员 | `steer`（插入当前 turn） |
| `control` | 控制指令，立即生效 | **仅群主** | `steer` + 标记 + 穿透静默 |

**为什么 `control` 限群主：** 任何人可发 `urgent` 不会造成灾难（最多是多插一句话）；任何人可发 `control` 就能随时打断全员，那是骚扰工具。

### 3.2 停止是一个状态，不是一条消息

这是今天翻车的直接修复。

```js
group.control = {
  stopped: true,
  reason: '...',
  byPersonId: 'm-...',
  at: 1759...
}
```

**投递规则：**

```
group.control.stopped === true
  ├─ 普通/紧急消息 → 只进 feed，不唤醒（可读，但不打断）
  └─ control 类消息 → 总是投递（否则解除指令自己也会被静默吞掉 ← 今天就是这个）
```

**为什么必须是状态：**
- 状态可以被**查询**（`a2a_goal_status` / `a2a_group_summary` 返回 `control.stopped`），人不靠记忆
- 状态可以被**新进入者**看到（入群返回带），避免「新人不知道现在静默」
- 状态**必须显式解除**，没有 TTL——因为「停止」本身是人为决定，自动恢复会让人以为停了其实没停

### 3.3 两个新工具

```js
a2a_group_control({ groupId, action: 'stop' | 'resume', reason })
  // 群主专用。stop 之后全员静默；resume 解除。
  // 返回里必须回显当前状态，避免「我以为解除了」。

a2a_group_post({ ..., priority: 'urgent' })
  // 普通发言的加急版本，任何成员可用。
```

**`a2a_group_control` 不是「发言」，所以它：**
- 不消耗 feed 的普通条目语义（写一条 system 行记录状态变更）
- 在静默期间仍然有权投递（否则 `resume` 永远发不出去）

## 四、做不到的部分（必须写清楚）

### 4.1 真·强制中止做不到

`steer` 是把文本**插入**正在运行的 turn，不是**终止**它。Agent 看到「立即停止」后自行决定停下——**这是提示级强制，不是硬中断。**

`deliver.js` 头部注释已经写明：

> reference bus, A2A has no `interrupt` mode

要真中断，需要 DSH 的 Agent 暴露 `abort()` 一类方法。目前 `agent` 只有 `followup` / `steer` / `inject`。**这条要等上游能力，不在本版。**

### 4.2 哪些场景够用，哪些不够

| 场景 | `control` + `steer` 够不够 |
|---|---|
| 「先别继续讨论了，等我决定」 | ✅ 够 |
| 「线上出事了，全员停手」 | ⚠️ 够但不硬——agent 可能正在一个长工具调用里 |
| 「立刻取消你正在执行的那条命令」 | ❌ 不够，需要 abort |

**诚实的边界：本版解决「话能插进去且不被静默吞掉」，不解决「正在执行的动作能被强制中断」。**

## 五、验收

```
□ 停止指令之后，普通消息只进 feed 不唤醒；发起人不再需要「记得解除」
□ resume 指令在静默状态下仍能投递（今天的关键失败点）
□ control 只有群主能发，普通成员发 → not_owner
□ 未使用优先级的群/消息：存储与工具返回与 0.1.25 逐字节一致
□ urgent 消息在目标正在运行时被插入，而不是等下一轮
□ a2a_group_control 返回回显当前状态（stopped 与否 + 原因 + 谁在什么时候设的）
```

**第 4 条是硬线**——和「未启用组织形态的群零影响」同一条原则。

## 六、和既有机制的关系

| 既有 | 关系 |
|---|---|
| `group/post` 的 `mentions` | `mentions` 决定**谁被唤醒**；`priority` 决定**唤醒得多急**。两个维度，正交 |
| `a2a_group_wait` | 等待的是「有新消息」，`control` 消息也应算新消息（否则等待者会漏掉停止指令） |
| `deliver.js` 的 `defaultMode` | 本机制是**按消息**覆盖；`defaultMode` 仍是**按接收方**的兜底 |
| 组织层 `goal_challenge` | challenge 是「质疑目标」，control 是「暂停投递」。后者不需要理由成立，前者需要 |
