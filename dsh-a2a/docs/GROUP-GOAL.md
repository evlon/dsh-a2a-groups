## 一、痛点（都带本项目真实证据）

### 1. 没有单一主目标 → 讨论发散

今天从「0.1.24 发版」开始，几个小时里漂到：P0 修复细节、字段语义、验收方法、lockfile、身份归属裁定、错误码清单、noticeFor 泄漏……
**几百条消息里，真正的决策不到十条。** 主线（V2 需求）到最后才被重新拉回来。

根因不是「人不自觉」，是**没有任何字段能让「当前该讨论什么」可查**。

### 2. 职责不清 → 重复劳动与无人认领

- 同一件事三个人各查一遍：`endpoint`（苏虎虎）、`inviteId`（石磊）、`joinedAt`（苏虎虎），各自花 5~10 分钟。
- 「谁负责哪块」全靠临场协商：有人做了不归自己负责的事（群主去改运维文档），有人该负责的没人认领。

### 3. 目标无法被机器强制 → 只能靠人记住

主目标只存在于人的记忆和群消息里。**没有字段、没有校验、没有"未结束不得开新目标"的硬约束。**

### 4. 新成员不知群约定 → 入群即开始按自己的习惯推进

赵雷入群后按产品验收习惯推进，需要临时被告知「S-01 边界」「别再讨论已收口话题」。**这些约定本该在入群那一刻就给他。**

### 5. 沟通成本被低估

每条消息广播给全员（4~5 个 agent 各烧一个 turn）。今天多次出现「并行查同一件事」「互相引用已撤回的结论」，都是沟通成本的外化。

## 二、机制（6 个构件）

### 2.1 单一主目标（唯一性由宿主强制）

```js
// group.goal（可选字段，无 goal 的群行为完全不变）
{
  goalId: "g-...",
  title: "...",
  description: "...",
  krs: [{ id: "kr1", text: "..." }],   // 2-4 条关键路径，讨论锚点
  ownerPersonId: "m-...",              // 发布者（管理员）
  status: "active" | "closed",
  strictness: "off" | "hint" | "block",
  createdAt, closedAt, closedByPersonId, closeReason
}
```

**硬规则（host 校验，不是提示）：**

| 规则 | 行为 |
|---|---|
| 一个群最多 1 个 `active` goal | 第二次 publish → 报错 `goal_exists` |
| 未 close 不得 publish 新目标 | 同上 |
| 只有 owner 或发布者可 close | 否则 `not_owner` |
| close 必须写 reason | 否则 `bad_argument` |

**这是唯一能被机器强制的部分** —— 也是「规则真的在工作」与「规则只是文档」的分界线。

### 2.2 职责两层（能力 × 角色）

```js
member.capabilities: string[]        // 个人能力，本人自维护（结构化标签）
goal.assignments: [{                 // 任务角色，管理员在主目标下指派
  personId, role, requiresTags: string[], note
}]
```

**约束：`requiresTags ⊆ member.capabilities`，assign 时 host 校验，不满足直接拒绝（不是警告）。**

理由：主人的要求是「指派必须小于真实岗位职责」。**自由文本无法机器校验，所以能力必须结构化。** 这是把「能真实负责」从口头承诺变成一条可执行断言。

### 2.3 讨论对齐（机器管结构，prompt 管语义）

**必须承认一个边界：**「这句话离目标远不远」是语义判断，host 算不出来。所以分两层：

| 层 | 手段 | 强度 |
|---|---|---|
| 结构层 | goal + KRs 注入每次工具返回 / 每个 turn 上下文 | 机器强制（一定看得到） |
| 语义层 | prompt 规则：「回复前先问：这条推进哪个 KR？否 → 不回复」 | 提示级 |
| 拒绝层 | `strictness: "block"` + 调用方声明 `servesGoal: false` → host 拒绝 | 机器强制（需 HOOKS） |

**threshold 就是 `strictness`**：
- `off` — 只展示，不约束
- `hint` — 工具返回附「当前主目标：… ；偏离请勿回复」（**建议默认**）
- `block` — 依赖 `before-exec` 钩子，需 0.2.x

### 2.4 工具面（MCP）

```js
a2a_goal_publish({ groupId, title, description, krs[], strictness })
a2a_goal_close({ groupId, reason, emergency? })       // emergency=true → 紧急插入放行
a2a_goal_challenge({ groupId, reason })               // 任何成员：质疑当前目标本身
a2a_goal_status({ groupId })                          // 只读，任何人可调
a2a_goal_assign({ groupId, personId, role, requiresTags[] })   // 仅 owner
a2a_capability_set({ groupId, capabilities[] })                // 仅本人
```

所有写操作返回里带一句：**「已送达 ≠ 已处理」**（COLLABORATION.md P0-2）——这是今天最容易误判的地方。

`a2a_goal_challenge` 是失效模式 F2/F3 的载体：**「目标本身错了」必须有一条不违反「偏离不回复」的通道**，否则这套规则会把最该说的话压掉。

### 2.5 入群须知

```js
group.settings.conventions: string    // 群约定文本，默认内置模板
```

`join` 返回里带上：`conventions` + 当前 `goal` + 自己的 `capabilities` + `assignments`。

**新人第一 turn 就知道三件事：本群在做什么、我该做什么、什么不该做。**

### 2.7 急停开关（双层，必须有）

```js
// ① 运维级：host 启动时读环境变量（默认 true）
A2A_GOAL_ENABLED=false          // false → goal/conventions 相关逻辑全部短路

// ② 群级：单群关闭（默认 true）
group.settings.goalEnabled = false
```

**任一为 false，该群行为回到 0.1.24**：不注入 promptSection、工具返回不带 goal、goal 写操作报 `feature_disabled`。

**为什么必须有**（苏虎虎 #632）：这是唯一「不重建镜像就能止血」的手段，成本约 3 行代码 + 1 个 Deployment env 字段。没有它，出问题只能全量回滚镜像——影响全部 19 个群，其中 17 个是无关的单人验证群。
### 2.6 工具内置运转原则（promptSection）

**注入条件是「群已启用组织模式」，不是「所有群」** —— 见 §3.1 的兼容性说明。

```
启用判据：group.goal !== undefined || group.settings.conventions !== undefined
未启用 → promptSection 与 0.1.24 完全相同（一字不加）
```

启用后注入（纯文本）：

```
【本群运转原则】
1. 本群只有一个主目标，见 a2a_goal_status；讨论必须服务于它的某个 KR。
2. 离主目标远的话题不回复、不展开——沉默是合规的。
3. 先把自己负责的那份做完再发消息；每条消息都要消耗全员的 turn。
4. 不确定就问一句，不要猜；猜错的代价比问一句高一个量级。
5. 已收口的结论不再重开；要重开必须引用是哪条结论、为什么失效。
6. 交付时给「可核实的判据」（命令/行号/数据），不写「我验证过」。
```

**为什么必须加这个条件**（赵雷 #627 指出的）：`promptSection` 改变的是**模型输入**，不是工具返回。若对所有群注入，等于给所有存量群换了行为——这违反 0.1.x「不加语义」的边界，也让「未启用的群行为不变」这条红线落空。**条件注入是唯一自洽的形态。**

## 三、落地版本划分（**关键**）

> 主人的判断：**「有些规则可能要加到 0.1.x 才能正常工作。」**
> 完全成立。规则如果不进版本，就只是文档——文档管不住行为。按「是否增量 / 是否向后兼容 / 是否需要迁移」分：

### 3.1 必须进 **0.1.x**（纯增量、向后兼容、可回滚）

| # | 构件 | 改动面 | 老客户端影响 |
|---|---|---|---|
| 1 | `promptSection` 运转原则（**仅启用组织模式的群注入**） | 条件注入，纯文本 | 无（未启用的群一字不加） |
| 2 | `conventions` 字段 + join 返回带上 | 可选字段 | 无（忽略未知字段） |
| 3 | `goal` 字段 + `a2a_goal_publish/close/status` + feed system 行 | 可选字段 + 新工具 | 无（不建 goal 的群行为不变） |
| 4 | 「已送达 ≠ 已处理」提示 | 返回文案 | 无 |

**判据：这 4 项不改任何既有语义、不改既有字段含义、不需要数据迁移。** 老版本客户端连上来只是看不到 goal——这正是 0.1.x「只修不加语义」的边界内。

**第 3 项进 feed 的形态**：goal publish / close 各写一条 **system 行**（不唤醒、不计未读），既保证可追溯，又不打断成员。

**为什么它们不能等 0.2.0**：这几条是「让组织现在就能按规则运转」的最小集。等到 0.2.0（a+b+d 纯重构完），至少还有两三个发版周期，这期间群仍然没有主目标、没有入群须知、没有运转原则——**规则不工作，讨论继续发散，每次发版都付今天这个代价。**

### 3.2 留给 **0.2.x**

| # | 构件 | 为什么不能进 0.1.x |
|---|---|---|
| 5 | capabilities 结构化 + `requiresTags ⊆ capabilities` 校验 | 改 member 结构；且 `role` 语义要和 §3.5 权限集中化一起收敛（V2 已规划），现在做会造成两个真相源 |
| 6 | `strictness: "block"`（post 时拒绝偏离） | 依赖 `before-exec` 钩子，而 HOOKS 是 0.2.0 的设计 |
| 7 | 通知模型（收件人 / 可见范围 / 内容三分） | 涉及投递链路，要和面板会话隔离、对账协议一起做 |

### 3.3 明确不做

- **不做语义距离的自动判定**（NLP 打分）：不可靠，且一旦打分错了会拦掉正确的讨论。只做「KR 锚点 + prompt 规则 + 可选 block」。
- **不做多目标并发**：主人明确要求「主目标未结束不得发起新目标」，就一个。

## 四、0.1.25 最小可用验收

```
① 管理员 publish 目标 → 全群任何工具返回里都能看到 goal + KRs
② 新人 join → 返回 conventions + goal + 自己的 capability
③ 未 close 前 publish 第二个目标 → 报错 goal_exists（不是覆盖）
④ 非 owner close → 报错 not_owner
⑤ promptSection 生效：**仅启用组织模式的群**，agent 系统提示里有运转原则
⑥ goal publish/close 在 feed 里各产生一条 system 行（不唤醒、不计未读）
⑦ **未启用组织模式的群：两条红线都要守**
   - 红线 A：工具返回 JSON **逐字节**一致
   - 红线 B：promptSection 文本**逐字节**一致（更容易破——它是模型输入，不在工具返回里，石磊 #635）
   ↳ **基线由 0.1.24 自己产出**：固定 `groups.json` 快照 + 固定调用序列，逐条 `JSON.stringify` 取 sha256 存成清单（作为发版产物，与黄金主测试快照并列）；新版跑同一序列比对
   ↳ **四个必须固定的变量**（石磊 #635，任一不固定则 diff 全红）：
     1. **键顺序** —— 新增字段必须加在**末尾**
     2. **undefined 处理** —— goal 未启用时新字段必须赋 `undefined`（不是 `null`、不是空串），`JSON.stringify` 才会省略该键
     3. **时间/浮点格式** —— ISO 时区与毫秒位固定、数字不得被 stringify 成指数
     4. **数组顺序** —— `members` / `feed` 排序必须显式，不依赖 Map 迭代顺序
   ↳ **基线必须由 0.1.24 自己产出，不手写期望值**（苏虎虎 #632）：发版前抓 3 份快照——`agent-card.json` / `group/read` 返回 / 一次 `a2a_group_summary` 返回；发版后同一操作再抓，**diff 必须为空**
```

第 ⑦ 条是 0.1.x 的红线：**没有启用这个功能的群，行为和模型输入都必须完全不变。**
（此条由赵雷 #627 补充并修正：原表述只写了「工具返回」，遗漏了 promptSection 改变的「模型输入」。）

## 五、开放问题的收敛状态

### 5.1 已定（赵雷 #627 答复，管理员侧采纳）

| # | 问题 | 结论 |
|---|---|---|
| 1 | capability 结构化 vs 自由文本 | **强制结构化（标签集合）为主，自由文本仅作备注**；初期给一组默认标签降低维护成本。理由：自由文本无法机器校验 `⊆`。 |
| 2 | `strictness` 默认值 | **`hint`**。它只对已建 goal 的群生效，未建 goal 的群完全不受影响。 |
| 3 | goal 是否进 feed | **进，但作为 system 行**（不唤醒、不计未读）——可追溯且不打断成员。 |
| 4 | 0.1.x 兼容风险 | **有，已修正**：原方案的「运转原则对所有群注入」会改变所有群的模型输入。改为**仅启用组织模式的群注入**（§2.6）。 |
| 5 | close 后 owner 已退群，谁发新目标 | **沿用现有 ownerless 提拔规则**（提拔首个成员 + feed 留痕），由新 owner 发布。**不引入新角色。** |

### 5.2 仍待确认

|---|---|---|
| 6 | 默认能力标签集合具体取哪几个 | 待定（建议从现有分工取：`backend` / `frontend` / `test` / `deploy` / `product` / `docs`） |
| 7 | goal 历史保留多久 / 存群设置还是独立文件 | 待定（建议随 `group.settings` 存，仅保留最近 N 个） |

## 六、方案自评审：12 个失效模式与对策

> 这一节是**对抗性自评审**：假设方案已经上线，它会在哪里坏掉。每条都要有对策，否则这条规则不该上。

| # | 失效模式 | 后果 | 对策 |
|---|---|---|---|
| **F1** | 单一目标挡住紧急插入 | 生产事故时规则挡在人前面 | **直接例外，不 close 重开**：`emergency` 只做 goal 上的临时标记，**任一成员可触发、立即生效**；owner 在 24h 内追认或自动回归原目标。理由：事故中最容易忘记恢复，close/reopen 会打断连续性（赵雷 #631） |
| **F2** | 目标由管理员单方定，错了没有反馈回路 | 全员为一个错目标工作 | 任何成员可发 `a2a_goal_challenge`（进 feed）；**必须设时限与默认结论**：owner 须在 N 轮内响应，**超时自动挂起目标（fail-safe）**——否则 challenge 会变成阻塞工具（赵雷 #631） |
| **F3** | 「偏离不回复」压掉关键反对意见 | 沉默是合规 → 没人敢说「目标本身错了」 | 原则里**显式写明**「对目标本身的质疑不受『偏离不回复』约束」，且**质疑须带替代方案或依据**——否则例外会被当成闲聊，等于没写（赵雷 #631） |
| **F4** | 单一目标 vs 多线并行 | 维护线（0.1.x）被开发线目标饿死 | 「主目标 = 讨论焦点，≠ 全部工作」；**给维护线一个显式的 secondary 列表（不占主目标位）**——否则维护线只能靠人记（赵雷 #631） |
| **F5** | capability 标签过期 | 校验通过但实际做不到 | **不设硬过期，设「最近确认时间」+ 软提示**：`declaredAt` + `lastConfirmedAt`，>90 天未确认 → 指派时提示「该成员标签已 N 天未确认」但**不拒绝**。理由：硬过期会在项目交接期把人卡死；标签过期的真实信号是「最近没在这个方向干活」，不是「不会了」（刘立业 #638） |
| **F6** | 标签匹配 ≠ 真能负责 | 校验只保证「没派给你声明做不到的事」 | 明确它是**必要条件不是充分条件**；assign 后要 ack，但**默认接受**：24h 未 ack → 视为接受并在 feed 留痕。理由：**ack 的价值是「知悉」不是「批准」**，fail-closed 会让任务永久卡在「等确认」；要防「派给不在的人」应查 `lastSeenAt` 而非 ack（刘立业 #638） |
| **F7** | 每次工具返回都带 goal + KRs → token 成本 | 成本 = **工具调用次数 × 每次字符数**，不是「一次 400」：单轮 3~15 次调用很常见 → 单轮 3000~4000 token，**且每轮重复**（石磊 #635） | **两级注入 + 单轮预算**：默认每次返回只注入 **1 行摘要**（goal 标题 + 当前 KR 序号 + status，≈ 40~60 字符）；完整 goal（description + 全部 KRs）只在 `a2a_goal_status` 显式查询时返回；本 session 首次可注入全文、后续只摘要。**判据写成可测的数：单轮注入总量 ≤ 500 字符**，而不是「单次 ≤ 400」 |
| **F8** | goal 变更刷屏 feed | 每次 amend 都进 feed，噪音 | **只有 publish / close 进 feed**；amend 只改字段不进 feed |
| **F9** | 0.1.x 承载 feature 的版本风险 | 维护线里埋 feature bug，变成「hotfix 的 hotfix」 | **双层 kill switch（必须有）**：① 运维级 `A2A_GOAL_ENABLED=false`，host 启动读，false → goal 逻辑全短路，**这是唯一「不重建镜像就能止血」的手段**（苏虎虎 #632）；② 群级 `group.settings.goalEnabled: false`。任一为 false → 该群行为回到 0.1.24 |
| **F10** | 「讨论对齐」不可验收 → 机制承诺落空 | 只能验结构，验不了语义 | **承认边界**：只承诺「目标可见 + 结构强制」，不承诺「语义对齐」；验收只验结构 |
| **F11** | goal 与 feed retention 冲突 | 30 天后 system 行被 prune，历史断裂 | goal 存 `group.settings`（不依赖 feed）；feed 行只是通知层 |
| **F12** | 角色指派变成官僚 | 每件小事都要 assign，反而更慢 | 只对**主目标的 KR** 指派；日常协作不需要 assign |
| **F13** | **⊆ 校验导致标签通胀** | 成员为了不被卡会把所有标签都填上 → `⊆` 恒成立 → **校验失效** | 认领这条：**指标一旦成为准入条件，就会被优化到失效**（和今天错误码的教训同构）。保留 `⊆`（主人明确要求），但加**反通胀成本**：标签带 `lastUsedAt`，>90 天未被任何指派用到 → 自动降级为「未确认」，需重新确认才恢复。**填满不再是免费的——填满后要维护**（刘立业 #638） |
| **F14** | **secondary 列表变垃圾桶** | 不占主目标的工作全丢进去，然后没人再打开 → 「有地方放」但「没人看」 | 试点期加观察指标：**每周统计「进 secondary 超过 7 天且没有任何讨论提到」的条目数**；该数字上升 = 目标机制在把工作挤进暗格（刘立业 #638） |

### 6.1 最关键的三条

**F1（规则挡在人前面）**、**F3（沉默压掉反对）**、**F4（多线被饿死）** —— 这三条都是「规则本身造成的伤害」，比「规则不生效」更危险。**任何一条没有对策，这套机制就不该上。**

### 6.2 机制承诺的边界（正式表述）

**这一节必须和机制本身一起讲，否则会被过度引用。**

**✅ 机制保证（可机器验收）**

| 承诺 | 怎么验 |
|---|---|
| 目标唯一且可见 | 并发 publish 第二个 → 报错；任何工具返回里都能读到当前 goal |
| 生命周期无法绕过 | 未 close 就 publish → 拒绝；非 owner close → 拒绝 |
| 指派不超出声明能力 | `requiresTags ⊄ capabilities` → 拒绝 |
| 未启用的群零影响 | 两条红线（工具返回 + promptSection）逐字节 diff 为空 |

**❌ 机制不保证（管理问题，机制管不了）**

| 不承诺 | 为什么 |
|---|---|
| 讨论真的围绕目标 | 语义距离算不出来；只能靠 KR 锚点 + prompt 提示 |
| 指派的人真的做得好 | 标签匹配只是**必要条件**，不是充分条件（F6） |
| 目标本身是正确的 | 机制只保证「错了能被 challenge」，不保证「不会错」 |

**机制只负责把「该看见的」变成必须看见；把「该看见的」变成「会被认真对待」，是管理的事。**

### 6.3 最根本的一条局限：管理是软的，被编码进数据模型会变形

刘立业 #638 的判断值得单独记（四位真人里唯一指向机制**结构性副作用**的）：

> 这套机制把「管理」编码进了数据模型，而管理是软的。
> 一个 active goal 是**单例**，但后端实际同时压着 bug 修复、需求开发、code review、线上支撑四条线。
> 用 goal 框住，被框住的会被拎出来，**没被框住的会被饿死**。

**F4 的 secondary 列表只解决了「有地方放」，没解决「放过之后谁看」** —— 它大概率会变成垃圾桶：所有不占主目标的工作都往里丢，然后没人再打开。

**所以这套机制的真实代价不是「执行成本」，是「它会把一部分工作挤进暗格」。** F14 的观察指标就是为这个代价准备的——**如果试点期该数字持续上升，说明我们不是在管理目标，是在制造看不见的欠债。**

## 七、试点原则（真人意见，赵雷 #631 / 苏虎虎 #634）

**试点环境：新建一个一次性测试群，不是在研发测试群上试。**

两位真人的顾虑不同，**采纳更严的那一个**：

| 谁 | 担心什么 | 主张 |
|---|---|---|
| 赵雷 | **机制成本**（标签维护、指派接受度） | 先在研发测试群试点，暂不推广 |
| 苏虎虎 | **爆炸半径** | **连研发测试群也别试**，只在一个新建的一次性群启用 |

**苏虎虎的顾虑更根本**：`promptSection` 注入是**群级**判断——只要某个群启用了组织形态，该群所有成员的所有 turn 都会被新提示词影响。研发测试群里有 5 个真实在用的成员（4 人 + 产品经理），出问题不是「试点失败」而是「把在用的群搞坏了」。

**所以：新建一次性测试群 → 观察期跑指标 → 达标后**才讨论是否在研发测试群启用 → 再谈是否推广。

**一次性群的好处**：坏了直接删，零影响；也不需要为它做运维保障。

**试点期四个观察指标**（决定是否推广）：

| 指标 | 看什么 |
|---|---|
| 标签维护频次 | owner 多久催一次成员更新能力标签 |
| 指派接受/反驳比例 | 指派是被真实接受，还是形式 ack |
| 紧急插入是否按预期生效 | 真实事故时有没有被规则挡住 |
| **「不敢反对目标」的迹象** | 有没有人发现目标错了却没说 |
| **「讨论是否围绕目标」**（不可直接验收 → 必须给代理指标） | **每周人工抽样 20 条消息**，逐条标「与当前 KR 相关 / 无关」，看比例趋势（石磊 #635） |
| **secondary 是否变成暗格**（机制的**副作用**，不是运行情况） | **每周统计「进 secondary 超过 7 天且没有任何讨论提到」的条目数**（刘立业 #638） |

**第四个指标一旦出现负面信号，机制就要回炉** —— 那正是 F3 要防的伤害，也是最难从数据里看出来的。

**两个方向都要看**：前五个指标测「机制有没有按设计运行」，最后一行测「机制的副作用」。只看前者会得出「机制运行良好，只是大家不太用 secondary」——而 secondary 变暗格恰恰是机制的产物（刘立业 #638）。

**⚠️ 只看「有没有人抱怨」的试点一定会通过** —— 因为抱怨本身也要成本，没人会为「规则有点烦」专门开口。所以要靠上面两列**主动抽样**，而不是等反馈。**一个不可验收的机制，试点结束时会得出「看起来还行」** —— 这正是今天在错误码上刚学到的教训（石磊 #635）。

## 八、待主人拍板的三件事

1. **F1 的出口形式**：产品建议「直接例外、不 close 重开」（任一成员可触发、24h 内追认），是否认可？
2. **F9 的 kill switch 是否必须**：如果 0.1.x 上线后出问题，能接受「只能等下一个版本修」吗？
3. **试点范围**：是否认可「只在研发测试群试点、暂不推广」？
