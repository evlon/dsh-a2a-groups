# V2（0.2.0 重构线）设计文档

> 状态：**草案，待 Lead 评审**。本文档是 v0.2.x 重构线开工前的设计预研，只做架构决策，不改代码。
>
> 与既有文档的关系：本文档回答「0.2.0 要改什么、为什么、怎么迁移」，是 `DESIGN.md`（0.1.x 定稿）的演进稿，不是替代。所有结论基于通读代码与文档的实证，非凭空想象。

## 一、现状痛点（实证，非猜测）

### 1.1 五个「神级文件」

通读 `lib/` 与 `client.js` 后的行数（2026-11-07 实测）：

| 文件 | 行数 | 塞进了一个文件的职责 |
|---|---|---|
| `lib/core/groups.js` | 2978 | 30+ 常量 + 密码学工具（`sha256Hex`/`constantTimeEquals`）+ 群状态机 `createGroupStore` + 文件 I/O（`writeFileAtomic`）+ 校验工具（`normalizeTags`/`requireText`/`deepFreeze`） |
| `lib/shared/tool-runtime.js` | 2015 | 26 个工具的执行体全部塞一个 `createToolRuntime` 闭包 |
| `client.js` | 4558 | 整个浏览器面板：侧栏、成员栏、名片、设置表单、邀请对话框、rejoin 逻辑 |
| `lib/index.js` | 1382 | 插件入口 `apply()` + 三个面板 RPC handler（`setPanelProfile`/`setPanelInvite`/`setPanelConfig`）+ 配置渲染（`renderConfigSection`）+ 快照发布（`publishGroups`）+ presence 心跳 |
| `lib/core/skills-group.js` | 1379 | 25 个 `group/*`/`person/*` skill 全塞一个文件 |

**为什么这是问题**：

1. **改一个功能要读完全不相干的代码**。比如 0.1.24 加「设置表单」，要同时读懂 `groups.js` 的常量、`index.js` 的 RPC 通道、`client.js` 的 `SettingsForm` 组件——三个神级文件交叉。
2. **测试粒度被迫变粗**。神级文件只能整体 import，测一个函数要拉起整个模块的依赖链。
3. **并行开发互相踩**。Lead 与多个会话并行改 `index.js`/`client.js` 时，写冲突是常态（本轮实际发生）。

### 1.2 两个真相源的分歧（`STATE.md` 已记录）

`memberships.json`（本地）与 `groups.json → members[]`（宿主）是两个独立真相源，网络断开、宿主重启、进程换数据目录都会产生分歧。六种状态里有两种（3a/3b）是分歧态，其中 3b「本地已删、宿主还在」**物理上不可修复**（`personKey` 只存本地）。

**0.1.x 的应对是「标记 + 重试」**（`unreachableAt`/`leavingAt`），这正确但不彻底：分歧的根因是「两个真相源没有单一权威」，v2 应该正面回答这个问题，而不是继续打补丁。

### 1.3 工具层与 skill 层的隐性重复

`shared/tool-specs.js` + `tool-runtime.js`（26 个工具）和 `core/skills-group.js`（25 个 skill）是两层，语义上「工具给人用，skill 给 A2A 调用方用」，但**执行逻辑大量重叠**：

- `a2a_group_post`（工具）和 `group/post`（skill）都调用 `groups.post()`
- `a2a_group_read`（工具）和 `group/read`（skill）都调用 `groups.read()`
- …依此类推 25 对

**0.1.x 的处理**是「工具 runtime 直接 import 共享的 `groups`/`bridge` 逻辑，skill 也 import 同一份」，这避免了重复实现，但**没有一个显式的「执行层」抽象**——两层的参数校验、错误码映射、凭证传递是各自写的，容易漂移（`CONTRACT.md` 已经为「spec 与 runtime 1:1」加了测试守护，但守护的是工具层内部，不是工具层与 skill 层之间）。

### 1.4 面板全局快照 vs 会话绑定（`BACKLOG.md` 第 2 项）

群绑定到 `(sessionId, groupId)`，但面板快照是**全局注入**的（`webserver/index-inject` 阶段无会话上下文），导致 A 会话的群摘要也出现在 B 会话的 HTML 里。0.1.x 只用前端 `sessionId` 过滤，**数据仍在 HTML 里，不算真隔离**。

> ⚠️ **苏虎虎评审修正**：`(sessionId, groupId)` 的键结构本身有问题——生产真实踩过「DSH 重启 sessionId 变 → 身份丢 → 重新入群产生重复身份」。见 §3.4.1 ③，身份模型应从「会话级」改为「实例级」。这动摇了本节的键结构假设。

### 1.5 `role` 权限位与业务身份的历史耦合

`role`（owner/member）是权限位，业务身份（产品/研发）已拆到 `roleAbout`/`tags`（层 A），这个拆分是对的。但 `groups.js` 里 `role` 的语义仍在 40+ 个函数里散落，没有收敛成一个「权限判定模块」——新增一个「只有 owner 能做」的操作时，靠的是各处手写 `if (member.role !== 'owner')`，而不是一个 `canInvite()`/`canDecide()` 的集中断言。

## 二、设计目标

0.2.0 重构要达成的，按优先级：

1. **拆神级文件**，让每个文件回答一个问题、能被独立测试、能并行开发。
2. **收敛两个真相源**，给成员状态一个明确的权威模型，消除或大幅缩小分歧态。
3. **显式化「执行层」抽象**，让工具层和 skill 层共享同一份「业务操作 + 校验 + 错误码」，消除隐性漂移。
4. **隔离面板数据**，让快照真正按会话收敛，而不是「全局注入 + 前端过滤」。
5. **集中权限判定**，`role` 语义收敛到单一模块。
6. **不破坏迁移**：生产跑 0.1.23，`groups.json`/`memberships.json` 的持久化格式必须向后兼容（或提供显式迁移）。

**明确不做的**（保持 0.1.x 的产品边界，见 `PRODUCT.md`/`DESIGN.md` 第十二节）：不引入外部依赖、不换存储（除非有真实规模需求）、不改成微服务、不给宿主加模型、不做持续私聊。

## 三、架构方案

### 3.1 拆 `groups.js`：按「领域」而非「文件大小」

`groups.js` 2978 行应该拆成**垂直切片**，每个切片一个文件，都在 `lib/core/` 内（仍零 DSH 依赖）：

```
lib/core/
├── groups/
│   ├── constants.js        ← 30+ 常量（MAX_*, FEED_TAIL_LIMIT, ONLINE_WINDOW_MS…）
│   ├── crypto.js           ← sha256Hex / constantTimeEquals（密码学工具，纯函数）
│   ├── validate.js         ← normalizeTags / requireText / optionalText / clamp* / deepFreeze
│   ├── store.js            ← createGroupStore 的「存储 + 原子写」骨架
│   ├── membership.js       ← join / leave / requestJoin / decideRequest / claimJoin / removeMember
│   ├── posting.js          ← post / read / subscribe / mentions / rate-limit
│   ├── identity.js         ← personProfile / setPersonProfile / listPersons / touch / colleague 聚合
│   ├── direct.js           ← 一对一（sendPersonMessage / listPersonMessages / ack / isPersonOnline）
│   └── directory.js        ← listDirectory / 群管（rename / archive）
```

**关键**：`createGroupStore` 仍然是**唯一入口**（对外仍导出一个 factory，签名不变），只是内部由这些切片组装。这样：

- 现有 `tool-runtime.js` / `skills-group.js` / `index.js` 的 import 路径不变（仍 `import { createGroupStore } from './groups.js'`，或改成 barrel `./groups/index.js`）。
- 每个切片能被独立单测。
- 领域边界清晰：加「踢人」只改 `membership.js`，加「发消息」只改 `posting.js`。

### 3.2 拆 `tool-runtime.js`：按工具域分组

2015 行的工具执行体，按工具域拆成多个 runtime 片段，由 `createToolRuntime` 聚合：

```
lib/shared/runtime/
├── group-lifecycle.js   ← create / invite / join / leave / request / decide / claim
├── group-chat.js        ← post / read / wait / summary / members / set_card
├── group-admin.js       ← kick / rename / archive / approvals / directory
├── person.js            ← person_send / person_inbox / person_ack / inbox_check
├── serve.js             ← a2a_serve / a2a_self_check / a2a_discover / a2a_send / a2a_stream
└── index.js             ← createToolRuntime 聚合 + 统一错误码映射
```

**关键**：`tool-specs.js`（纯数据）**不拆**——它已经是最小契约单元，拆了反而破坏「spec 与 runtime 1:1」的测试守护。只拆 runtime 的执行体。

### 3.3 显式化「执行层」：引入 `operations/` 抽象

工具层（`tool-runtime`）和 skill 层（`skills-group`）重复的核心，抽成一个**业务操作层**：

```
lib/core/operations/
├── post-message.js    ← 校验 + 调 groups.post + 错误码映射（工具和 skill 共用）
├── read-feed.js
├── join-group.js
├── invite-member.js
└── …
```

**收益**：一个操作（比如「发帖」）的**参数校验、凭证检查、错误码映射、副作用**只写一次，工具层和 skill 层都调它。`CONTRACT.md` 的「spec↔runtime 1:1」守护升级为「spec↔operation↔skill 三向一致」。

**风险**：多一层间接。但 0.1.x 已经因为「两层各自写校验」踩过漂移，这一层是值得的。

### 3.4 面板数据按会话隔离（**苏虎虎评审修正：重点看身份模型**）

`BACKLOG.md` 第 2 项的正式解法：

- `publishGroups()` 不再「全局注入全部群」，而是注入「当前会话的群 + 一个空的占位」。
- 真隔离靠「前端带 `sessionId` 拉取」，即面板 RPC 通道新增 `groups-by-session` 端点，浏览器启动后按当前 sessionId 拉取，而不是吃 HTML 里的全局快照。

**迁移**：`__DSH_A2A_GROUPS__` 全局注入保留（兼容旧页面），但内容改为「元信息 + 空列表」，真实数据走 RPC。这样旧页面不崩，新页面拿到真隔离。

#### 3.4.1 三项补充（苏虎虎 Q3，逐条合入）

**① 必须有降级路径**（RPC 失败不能白屏）：

- 面板 RPC 拉取失败时，显示「最后已知状态 + 重连中」，而不是空列表或白屏。
- 最后已知状态缓存到本地（localStorage 或注入的 last-known snapshot），RPC 失败时兜底渲染。

**② 通道要明确**（面板数据不能和推送通道抢）：

- 面板数据走 `groups-by-session` RPC（**拉取**，一次性拿全量），推送走 SSE 订阅（**推送**，增量）。
- 两者职责分开：拉取负责「面板显示哪些群」，推送负责「新消息到达」。不混用，避免「面板刷新触发一次 SSE 重连」。

**③ 身份应「实例级」而非「会话级」（标红，最重要）**：

> ⚠️ **这是对原设计 §1.4 假设的重大修正**。苏虎虎在生产真实踩过：**DSH 重启后 `sessionId` 变了，身份丢失，被迫重新入群还产生重复身份**。

修正后的身份模型：

```
身份（personId + personKey）      ← 实例级：一台机器的一个人，跨会话、跨重启稳定
   │
   └── 会话（sessionId）          ← 只影响「面板显示哪个群」，不影响「以什么身份发言」
```

**含义**：

| 维度 | 原设计（会话级） | 修正（实例级） |
|---|---|---|
| 身份归属 | `(sessionId, groupId)` 决定身份 | **实例**决定身份，会话只决定「面板显示」 |
| DSH 重启 sessionId 变 | 身份丢，重新入群产生重复身份 | 身份仍在，面板重新绑定会话即可 |
| 同一机器两会话 | 两个身份 | **一个身份**，两个会话只是「两个视角」 |

**这条要单独标红进设计**，因为它动了 `memberships.js` 的**键结构**（从 `(sessionId, groupId)` 改为 `(instanceId, groupId)`），是 0.2.0 里唯一一个**不是纯搬代码**的改动，需要和 c（面板隔离）一起单独发版，或单独一个里程碑。

> **风险提示**：改键结构会影响「同一台机器两个会话两个成员」这个 0.1.x 的设计目标（`DESIGN.md` §7.2）。需要 Lead 决策：是「身份实例级」取代「身份会话级」，还是两者并存（实例级身份 + 会话级视角）。这个决策**不在本设计文档擅自拍板**，标为待 Lead 决策（见 §七）。

### 3.5 权限判定集中化

`groups.js` 里散落的 `if (member.role !== 'owner')` 收敛到 `lib/core/groups/permissions.js`：

```js
// 集中断言，返回 { ok, code } 而非 throw，供工具/skill 层统一映射
canInvite(member, group)
canDecide(member, group)
canRemoveMember(actor, target, group)
canRename(member, group)
canArchive(member, group)
```

**收益**：加一个「只有 owner 能做」的操作，改一个文件；权限语义（「owner 才能 X」）只在一处定义。

### 3.6 两个真相源的收敛（方向性，不强制在 0.2.0 全部落地）

`STATE.md` 已经说清「3b 物理不可修复」。0.2.0 能做的**方向性收敛**：

1. **本地账本权威化**：`memberships.json` 成为「我记的真相」，宿主成为「可恢复的副本」。本地账本加一个 `status` 字段（`active`/`leaving`/`unreachable`/`gone`），替代现在散落的 `unreachableAt`/`leavingAt` 双布尔。
2. **对账协议**：加一个 `group/reconcile`（或复用 `group/info`），成员定期对账「本地 vs 宿主」的成员状态，把分歧从「被动发现」变成「主动探测」。
3. **3b 的最后防线**：本地账本删除前强制写一个「tombstone」（保留 `personKey` 的 sha256 摘要，不保留明文），让「我是不是曾经是成员」可查，虽然仍不能恢复凭证，但至少能诊断。

> 这一条是**方向**，具体协议设计留到 0.2.0 实施时细化。0.2.0 的第一步（拆文件）不做 3.6，避免一次改太多。

## 四、迁移路径

### 4.1 持久化数据兼容（硬约束）

生产跑 0.1.23，`groups.json` / `memberships.json` 的格式**必须向后兼容**：

| 数据 | 0.1.x 格式 | 0.2.0 要求 |
|---|---|---|
| `groups.json` | `{ groups: { [groupId]: GroupRecord }, persons: {...}, directMessages: [...] }` | **不改变落盘结构**，只改内存里的代码组织 |
| `memberships.json` | `{ [sessionId]: { [groupId]: Membership } }` | **不改变落盘结构**，只增加可选字段（如 `status`） |

**原则**：重构是「代码组织」层面的，不是「数据格式」层面的。0.2.0 的第一步（拆文件）**零数据迁移**——`createGroupStore`/`createMembershipLedger` 的持久化读写在原地，只是内部逻辑搬了家。

**如果后续（3.6 对账协议）要加字段**：新字段一律**可选、有默认值、读旧数据时静默补默认**，绝不做「强制升级 schema」——生产群数据不能因升级而不可读。

#### 4.1.1 「零迁移」拆成四层验证（缺一不可）

> 依据苏虎虎（部署运维）评审意见：生产真实数据 `groups.json` version=1、19 群、178KB，成员字段含 `clientVersion`/`profileUpdatedAt`/`roleAbout`/`endpoint` 等可选字段。「零迁移」不能只是一句口号，必须拆成四层、每层可验证：

| 层 | 验证 | 为什么单独一层 |
|---|---|---|
| ① 读得进 | 0.2.0 读 0.1.x 的 version:1 数据 | 升级不炸，最低门槛 |
| ② 写得回 | 0.2.0 写回后，0.1.x **还能读** | 这才是「回滚能力」——只读得进、写回后旧版读不了，等于不能回滚 |
| ③ 不丢字段 | 0.2.0 不认识的可选字段**原样保留** | 最大风险是「字段静默丢弃」——0.2.0 重写时把 `profileUpdatedAt` 之类不认识的字段落掉，成员画像静默丢数据 |
| ④ 不重排/不改语义 | `keyHash` 算法不变、`nextSeq` 递增不变、`feed` 顺序不变 | 排序/哈希一旦变，回滚后消息顺序错乱、凭证校验失败 |

#### 4.1.2 四项验收（硬门槛）

| 编号 | 验收 | 具体做法 |
|---|---|---|
| **A** | 双向兼容测试 | 0.1.24 造数据 → 0.2.0 读 → 写 → 0.1.24 再读，四步 JSON 语义完全一致 |
| **B** | 字段保全测试 | 含所有可选字段的记录，执行 post/join/settings/archive 后，字段一个不少 |
| **C** | 回滚演练 | 升级 0.2.0 → 用**真实生产数据**跑 → 回滚 0.1.24 → 19 群全可读、成员能发言 |
| **D** | 格式快照 | `groups.json` 结构存成 schema 断言，字段增删要显式更新（防止「顺手加字段」破坏兼容） |

> **A/B/C/D 缺一不可**，是 0.2.0 发版的**前置条件**，不是「事后补测」。

### 4.2 分阶段落地（每阶段可独立验证、可回滚）

> 依据苏虎虎评审意见（Q4）**调整优先级**：`c`（面板会话隔离）是「行为变化」，不能和前四个「纯重构」混发——混发后出问题难判断是重构引入还是新逻辑引入。所以顺序改为 **a → b/d → c（单独发）→ e（最后灰度）**。

| 阶段 | 内容 | 性质 | 数据迁移 | 可回滚 |
|---|---|---|---|---|
| **0.2.0-a** | 拆 `groups.js` / `tool-runtime.js` / `index.js` / `client.js` 神级文件（纯搬代码，不改行为） | 纯重构 | 无 | ✅ 任何一阶段失败，回退 commit 即可 |
| **0.2.0-b** | 引入 `operations/` 执行层（工具/skill 共享校验） | 纯重构 | 无 | ✅ |
| **0.2.0-d** | 权限集中化 + 本地账本 status 字段 | 纯重构 | `memberships.json` 加可选字段 | ✅ 可选字段向后兼容 |
| **0.2.0-c** | 面板按会话隔离（RPC 拉取替代全局快照） | **行为变化** | 无 | ⚠️ 单独发版，与纯重构分开 |
| **0.2.0-e** | 对账协议（3.6） | **新行为** | 可选字段 | ⚠️ 移至 0.3.0，需灰度验证 |

**关键原则（修正版）**：

- **0.2.0-a / b / d 是「纯重构，零行为变化」**，用「黄金主测试快照逐字节一致」验收，**可以一次发版**。
- **0.2.0-c（面板会话隔离）是「行为变化」**，必须**单独拆出发版**——它改了「面板显示哪些群」这个用户可感知行为，混进纯重构会让「是重构引入 bug 还是新逻辑引入 bug」分不清。
- **0.2.0-e（对账协议）是「新行为」**，移到 0.3.0，单独发版、单独灰度。

**发版顺序**：`0.2.0（a+b+d 纯重构）` → `0.2.1（c 面板隔离，单独发）` → `0.3.0（e 对账协议）`。

**补充（苏虎虎）**：0.2.0 发布时保留 0.1.24 镜像可回滚，且**真拿生产数据演练回滚**——不是「写个回滚脚本」就算，而是拿 178KB/19 群的真实数据跑一遍「升 0.2.0 → 回滚 0.1.24 → 群全可读」。

### 4.3 测试守护（重构的安全网）

0.1.x 已有 764 个测试。0.2.0 重构的**前提**是：

1. 先补「黄金主测试」——针对每个公开 factory 的**行为快照**（输入→输出的完整断言），覆盖当前 0.1.x 的正确行为。
2. 拆文件时，黄金主测试**一行不改**。重构成功 = 黄金主测试全绿 + 单元测试数只增不减。
3. 每拆一个神级文件，新增「该文件内部各切片的独立单测」，把「整体可测」升级成「局部可测」。

#### 4.3.1 苏虎虎补充的四项验收（Q2）

> 苏虎虎指出「黄金主测试快照逐字节一致」**不够**，补四项——尤其第一项源自他的真实教训：pnpm 撞锁后「测试全绿但插件加载不了」。

| 编号 | 补充验收 | 为什么 | 具体做法 |

| **①** | 模块加载冒烟 | 测试全绿 ≠ 插件能加载（import 断链是测试覆盖不到的） | 容器内 `node -e` 逐模块 `import`，任何一个 import 断链即失败 |

| **③** | 反向用例纳入主测试 | 黄金主测试不能只覆盖 happy path | 越权、错 key、错 personKey、归档群发言——反向路径也进快照 |

### 5.1 概览

| # | 风险 | 严重度 | 可检测性 |
|---|---|---|---|
| 1 | 拆神级文件引入行为回归 | 高 | 高（测试可测） |
| 2 | `operations/` 层间接性，调试变难 | 中 | 中 |
| 3 | 面板会话隔离改动注入机制 | 中 | 高（HTML 可断言） |
| 4 | `memberships.json` 加字段后旧版本读不了 | 高 | 中（要混版本才能测） |
| 5 | 并行开发冲突 | 中 | 高（git 冲突可见） |
| 6 | 重构范围失控 | 高 | 中（靠流程约束） |
| 7 | **字段静默丢弃**（0.2.0 不认识的可选字段被落掉） | 高 | 中（要字段保全测试才能测） |
| 8 | **回滚被无声破坏**（0.2.0 写回后 0.1.x 读不了，但没被发现） | 高 | 低（要真实回滚演练才能测） |

### 5.2 每条详细展开

#### 风险 1：拆神级文件引入行为回归

- **触发条件**：搬代码时漏了某个 import、改了某个函数的默认参数、某处 `this` 绑定丢失、深层闭包被切开后共享状态断裂。
- **典型症状**：一个工具 100% 崩溃而测试全绿（0.1.x 实际踩过：三个核心工具曾因 ReferenceError 崩溃，测试只断言返回值没断言不抛错）。
- **缓解措施**：
  1. **黄金主测试先行**——每个公开 factory 先补「输入→输出完整快照」断言，覆盖 happy path + 拒绝 path + 拒绝无副作用。
  2. **重构前后快照逐字节一致**作为合入门槛，不是「测试通过」而是「快照相等」。
  3. 每拆一步跑全量 + 该切片的独立单测，**不攒到最后一起跑**。
- **检测信号**：黄金主测试快照 diff 非空 → 立即回退该 step。

#### 风险 2：`operations/` 层间接性

- **触发条件**：工具层和 skill 层都调 operation 后，出问题时要从「工具→operation→groups」三层定位；错误码如果没在 operation 层统一映射，还是散落。
- **典型症状**：一个工具报错，但错误码来自 groups 层原始 code 而非工具层稳定子码，调用方解析失败。
- **缓解措施**：
  1. operation 层只做三件事：**参数校验 + 调 groups + 错误码映射**，职责写死，不做业务决策。
  2. 错误码映射表集中在一处（operation 层），工具/skill 层只转发，不二次映射。
  3. 用测试断言「工具层的错误码 == skill 层的错误码」（两者调同一个 operation）。
- **检测信号**：工具层和 skill 层对同一业务错误的错误码不一致 → 说明映射又散落了。

#### 风险 3：面板会话隔离改动注入机制

- **触发条件**：`__DSH_A2A_GROUPS__` 改成「空占位」后，旧版插件/旧页面仍读它 → 群列表空白；或 RPC 端点没在「无会话上下文」时正确降级。
- **典型症状**：升级插件后，旧页面（没刷新）看到空群列表，误以为群全丢了。
- **缓解措施**：
  1. `__DSH_A2A_GROUPS__` 保留，内容改为「元信息 + 空列表」，**旧页面不崩**（只是空，不是坏）。
  2. RPC 端点 `groups-by-session` 在「无 sessionId」时返回空数组 + 明确状态，不抛错。
  3. 灰度：先只改快照内容，RPC 拉取作为第二提交，分两步验证。
- **检测信号**：抓 HTML 断言 A 会话不出现 B 会话的群；同时断言旧格式（全局快照）仍能渲染空态。

#### 风险 4：`memberships.json` 加字段后旧版本读不了

- **触发条件**：新字段不是「可选+有默认值」，而是被当作必填；或旧版代码对未知字段做了严格校验（`additionalProperties: false`）。
- **典型症状**：0.1.23 成员实例读到 0.2.0 写的 memberships.json，因 `status` 字段报错或静默丢弃整个记录。
- **缓解措施**：
  1. 新字段一律**可选、有默认值、读旧数据静默补默认**。
  2. 明确「数据兼容是单向的」：0.2.0 读 0.1.x ✅，0.1.x 读 0.2.0 **不承诺**（虽然 JSON 天然容忍未知字段，但要测）。
  3. **混版本测试**：专门写一个「0.1.23 格式的 memberships.json 被 0.2.0 读」的测试，断言补默认 + 写回带新字段。
- **检测信号**：混版本测试失败 → 说明新字段不向后兼容。

#### 风险 5：并行开发冲突

- **触发条件**：Lead 与多会话同时改同一个神级文件（index.js / client.js / groups.js）。
- **典型症状**：git 写冲突、checkout 冲掉未跟踪文件（**本轮实际发生**：我的 V2-DESIGN.md 在旧目录被 Lead 的 git 操作冲掉，靠 worktree 隔离解决）。
- **缓解措施**：
  1. **拆文件本身就是解药**——拆完后各会话改不同切片，写作用域天然不重叠。
  2. 过渡期（拆之前）用 **git worktree 物理隔离**（Lead 已为 v2 会话建 `E:\dsh-a2a-bus-v2`）。
  3. 每个会话在 bus 消息里声明 write_scopes，Lead 统一协调。
- **检测信号**：git status 出现预期外的未跟踪文件或冲突 → 立即停下对齐。

#### 风险 6：重构范围失控

- **触发条件**：重构时「顺手修个 bug」「顺手优化个函数」，边界越扩越大。
- **典型症状**：0.2.0 迟迟发不出来，且分不清「是重构引入的 bug 还是新功能引入的 bug」。
- **缓解措施**：
  1. **0.2.0-a~d 严格「零行为变化」**，验收标准是「快照相等」，不是「功能更好了」。
  2. 只有 0.2.0-e（对账协议）是新行为，且已移到 0.3.0。
  3. 任何「顺手改」都单独提一个 commit 或 issue，不混进重构 commit。
- **检测信号**：重构 commit 的 diff 里出现「非搬代码」的改动（改了逻辑而非移动位置）→ 打回。

#### 风险 7：字段静默丢弃（苏虎虎 Q1 层③）

- **触发条件**：0.2.0 重写 `groups.json` 时，用的是「白名单序列化」（只序列化认识的字段），把 0.1.x 写的可选字段（`clientVersion`/`profileUpdatedAt`/`roleAbout`/`endpoint` 等）静默落掉。
- **典型症状**：升级后成员画像的「负责什么」、客户端版本、最后活跃时间等字段消失，但**没有任何报错**——数据静默丢失是最难发现的。
- **缓解措施**：
  1. **字段保全测试（§4.1.2 B）**：含所有可选字段的记录，执行 post/join/settings/archive 后字段一个不少。
  2. **格式快照（§4.1.2 D）**：`groups.json` 结构存成 schema 断言，字段增删显式更新。
  3. 序列化用「**读什么写什么**」（preserve unknown keys），而不是「只写 schema 里的字段」。
- **检测信号**：字段保全测试失败 → 有字段被落掉。

#### 风险 8：回滚被无声破坏（苏虎虎 Q1 层②）

- **触发条件**：0.2.0 写回的数据，0.1.x **读不了**（比如 0.2.0 写了新字段但 0.1.x 用 `additionalProperties: false` 严格校验），但因为没有回滚演练，这个破坏**在上线前没被发现**。
- **典型症状**：回滚 0.1.24 后群列表空白、成员读不到消息，运维才发现「回滚不了」。
- **缓解措施**：
  1. **双向兼容测试（§4.1.2 A）**：0.1.24 造数据 → 0.2.0 读 → 写 → 0.1.24 再读，四步语义一致。
  2. **真实回滚演练（§4.1.2 C）**：拿生产 178KB/19 群数据，真跑「升 0.2.0 → 回滚 0.1.24 → 群全可读、成员能发言」。
  3. 0.2.0 发布时**保留 0.1.24 镜像**，确保能随时回滚。
- **检测信号**：回滚演练中「0.1.24 读不了 0.2.0 写的数据」→ 回滚能力被破坏，阻断发版。

## 六、与 0.1.x 的关系

- **0.1.x 继续是生产维护线**，只收 bug 修复，不做重构。0.2.0 的拆文件**绝不回迁**到 0.1.x（否则维护线就失去了「稳定、可回滚」的意义）。

- **发版节奏**：0.2.0 从 `v0.2.x` 分支发，走已定的「checkout tag → arm64 构建 → Harbor → 滚动更新」流程（见 `deploy/k8s/README.md`，苏虎虎已定稿）。只有 0.2.0 真正有宿主运行时改动时，才动生产宿主。

## 七、已定方向（Lead 初步决策，待评审确认）

4. **`client.js` 4558 行拆分**：**单独里程碑**（0.2.x 之后的独立工作项），别和 host 侧重构耦合。

5. **【新增，苏虎虎 Q3 引入】身份模型「实例级」vs「会话级」**：苏虎虎生产踩过「DSH 重启 sessionId 变 → 身份丢 → 重复身份」。这挑战了 0.1.x 的 `(sessionId, groupId)` 键结构。三个选项待 Lead 拍板：
   - **A**：身份彻底实例级，`memberships.json` 键改 `(instanceId, groupId)`，会话只做「面板视角」。放弃「一机两会话两个成员」。
   - **B**：并存——实例级身份为主，会话级视角为显式覆盖（默认实例身份，除非会话显式声明独立身份）。
   - **C**：维持 0.1.x 会话级不变，0.2.0 不碰键结构，只做「面板按会话过滤」（把身份问题留到 0.3.0）。
   
   > 这是 0.2.0 里**唯一可能动键结构**的点，影响迁移复杂度，必须 Lead 先定。默认倾向 B（兼顾稳定身份 + 保留多会话能力），但需产品确认「一机两会话两成员」是否还是真实需求。

> 这些方向已反映在下方 §4.4 的详细拆解里。
