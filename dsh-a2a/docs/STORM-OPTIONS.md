# 群聊风暴：两种方案的可行性评估

> 结论先行：**收缩方案的 90% 已经建好了，缺的只是让它可配置**。借鉴团队的方案成本高一个数量级，
> 而且解决的是不同的问题。

---

## 一、先看清楚：现在到底怎么工作

### 已经存在的分级

`lib/sh/inbox.js` 的 `gradeOf()`：

```js
export function gradeOf(post, membership, muted) {
  if (muted) return 'ambient';                       // 静音优先
  const mentions = post.mentions ?? [];
  if (mentions.length === 0) return 'notice';        // 没 @ 任何人
  if (mentions.includes('@all')) return 'mention';   // @所有人
  if (mentions.includes(membership.personId)) return 'mention';  // @我
  return 'ambient';                                  // @了别人，不是我
}
```

### 三段式的投递行为（**已经实现**）

```js
// lib/dsh/inbox.js:504
mode: grade === 'ambient' ? 'inbox' : 'queue',
```

| grade | mode | 行为 |
|---|---|---|
| `mention` | `queue` | **唤醒**一轮对话 |
| `notice` | `queue` | **唤醒**一轮对话 |
| `ambient` | `inbox` | **静默放入**，不唤醒 |

**`deliver.js` 的 `mode: 'inbox'` 注释原文**：

> `inbox` was seated without waking anything

### 那条断掉的线

`notice`（群里有人说话但没 @ 任何人）**和 `mention` 一样会唤醒**。

**这就是风暴的来源**：三个人各说各的，每条都不 @ 谁，于是每条都唤醒所有人。

```
张三发一条 → 李四醒 + 王五醒  = 2 次唤醒
李四回一条 → 张三醒 + 王五醒  = 2 次唤醒
王五回一条 → 张三醒 + 李四醒  = 2 次唤醒
一轮 3 条消息 → 6 次唤醒 → 每次唤醒都可能产生新消息
```

## 二、方案 A：收缩（只响应 @ 我的）

### 改动

**一处判断**：

```js
// 现在
mode: grade === 'ambient' ? 'inbox' : 'queue',

// 收缩模式
mode: (grade === 'mention' || config.groups.noticeWakes === true) ? 'queue' : 'inbox',
```

加一个配置项 `groups.noticeWakes`（默认 `false` = 收缩）。

### 可行性：★★★★★

| 项 | 状态 |
|---|---|
| `mentions` 解析 | ✅ 已实现（含 `@all`、名字→id、歧义丢弃） |
| 三级分级 | ✅ 已实现 |
| 静默投递 | ✅ 已实现（`mode: 'inbox'`） |
| **需要的改动** | **1 个条件 + 1 个配置项** |

**改动量：约 5 行 + 测试。**

### 优势

1. **风暴直接消失**：没 @ 人的消息不唤醒任何人
2. **成本几乎为零**：基础设施全在
3. **可逆**：配置项，随时切回
4. **消息不丢**：`inbox` 模式仍会放入队列，下轮可见
5. **符合直觉**：IM 软件都是这样——群消息不弹窗，@ 才弹

### 劣势

1. **群变得"安静"**：不 @ 人的话，没人会主动看到
2. **需要约定**：讨论必须 @ 人，否则对方不知道
3. **`@all` 可能被滥用**：一个 `@all` 唤醒所有人，风暴重现
4. **丢失"氛围感"**：真正的群聊需要"看到别人在说什么"，收缩后变成"任务分派"

### 缓解

- `@all` 加限流（每人每小时 N 次）
- 提供 `a2a_group_read` 让会话主动查看（已有）
- `a2a_inbox_check` 汇报积压（已有）

## 三、方案 B：借鉴智能体团队

### 需要建的东西

| 组件 | 我们的现状 | 工作量 |
|---|---|---|
| **任务板**（DAG + revision CAS） | 无 | 大 |
| **`wait_agent` 事件等待** | SSE + 50 秒心跳轮询 | 中 |
| **`send_message` 唤醒对方** | 消息排队等下次 turn | 中 |
| **角色分层**（Lead/teammate） | 群主只是权限概念 | 中 |
| **`writeScopes` 写入域** | 无 | 小 |
| **状态枚举**（running/inactive/...） | online/offline | 小 |

### 可行性：★★☆☆☆

**能做，但成本高一个数量级**，而且有个根本性障碍：

> **智能体团队的成员是同一进程内的 Agent，协作群是跨机器的独立 DSH 实例。**

这意味着：

| 团队能做到 | 群里做不到 |
|---|---|
| `wait_agent` 精确等某个成员 | 只能等「下一帧 SSE」 |
| `send_message` 直接 resume | 只能发消息，等对方轮询 |
| 内存中的任务板 | 需要跨机器一致性的持久化任务板 |
| 成员状态由进程直接报告 | 只能靠心跳推断 |

**`wait_agent` 是最关键的差异**：团队里它是「等下一个变化就返回」，群里只能「保持连接，来什么收什么」。前者精确，后者盲目。

### 优势

1. **真正的解法**：问题不在消息，在于**没有共享状态**
2. **交接不需要说话**：A 做完 → 任务状态变更 → B 的条件满足
3. **可审计**：任务有 revision 历史
4. **不会互相覆盖**：`writeScopes` 声明

### 劣势

1. **工期长**：任务板 + CAS + DAG 至少要一周
2. **跨机器一致性难**：CAS 需要宿主作为唯一权威
3. **改变产品形态**：从"聊天"变成"项目管理"，学习成本高
4. **可能过度设计**：三五个人的小群不需要 DAG

## 五、已落地（2026-11-05）

收缩方案已实现，走的是**已有但从未生效**的 groups.wakeMembers 配置，默认改为 false。

### 实际行为对照

| 消息 | grade | 改前 | 改后 |
|---|---|---|---|
| @all | mention | 唤醒 | **唤醒**（不变） |
| @我 | mention | 唤醒 | **唤醒**（不变） |
| @别人 | ambient | 静默 | 静默（不变） |
| **没 @ 任何人** | notice | **唤醒** | **静默** |

**唯一改变的是第四行。**

### 需要恢复群聊氛围时

    groups:
      wakeMembers: true

### 消息没有丢

静默只是**不唤醒**：mode inbox 仍会把消息放进队列（deliver.js 注释：seated without waking anything），
下一次自然检查时通过 a2a_inbox_check / a2a_group_read 一次性读全。

### 一个实现细节

这个配置原本**存在于 schema 和每群设置里，但没有任何代码读它**。现在改的是让它真正生效，而不是新增一个开关——
字段名本来就表达了这个意思。

代价：只做到了**进程级**，没做到每群粒度。原因是群存储的 snapshot 不暴露 settings，
读每群的值需要新造一条不存在的调用链。「没 @ 我该不该唤醒我」是人怎么工作的属性，不是某个群的属性，
所以单开关也说得过去。

## 五、我的判断

### 这两个方案不是二选一

**它们解决的是不同层次的问题**：

```
方案 A（收缩）：解决「不该唤醒的别唤醒」   → 消息层
方案 B（团队）：解决「不靠说话也能协作」   → 协作层
```

**先做 A，观察，再决定要不要 B。**

### 理由

1. **A 的 90% 已经在了**，改 5 行就能验证假设
2. **A 之后可能 B 就不需要了** —— 如果收缩后消息量降到可接受，任务板是过度设计
3. **B 的最大障碍是跨机器**，这个不会因为时间推移变简单

### 我建议的具体路径

**第一步（今天）**：加 `groups.noticeWakes` 配置，默认关闭

**第二步（观察一周）**：看实际消息量

**第三步（再决定）**：
- 消息量可接受 → 停
- 消息量仍高 → 说明是**任务依赖**问题，不是消息问题 → 做任务板

## 六、一个更便宜的中间选项

如果你担心「收缩后群变太安静」，有个**第三条路**：

**按消息序号节流，而不是按 @ 过滤。**

```js
// 一个"回合"内，只唤醒一次
if (post.seq - lastWokenSeq < THROTTLE) return 'ambient';
```

**效果**：连续 10 条消息只唤醒 1 次，但**没人会完全错过**。

**代价**：可能错过中间的某条重要消息。

**适合**：讨论密集但不需要逐条响应的场景。
