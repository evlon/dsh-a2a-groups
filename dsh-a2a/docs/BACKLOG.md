## 1. 群运营管理面板

**状态**：待设计，不实现
**提出时间**：2026-11-04
**优先级**：中（有真实需求，但不阻塞 MVP）

### 给谁用

**公司运营管理员**，不是群成员。这个区分决定了整个功能的设计。

### 要解决什么

一个公司里群会越来越多，管理员需要知道：

| 问题 | 为什么关心 |
|---|---|
| 现在有多少个群？ | 容量规划 |
| 哪些群还活着？ | 找出废弃群，回收资源 |
| 每个群多少人？ | 判断群是不是「建了没人来」 |
| 谁建的群？建了多少？ | 异常检测（某人建 50 个群通常意味着误用） |
| 多久没有活动？ | 归档建议 |
| 哪些群对外可见？ | 合规审计 |

### 关键约束：只看治理指标，不看内容

**管理员不能看群里的消息内容。** 这不是技术限制，是设计决定：

- 群成员加入时预期的是「同事之间说话」，不是「被管理员审阅」
- 治理需要的是**指标**（多少人、多久没动），不是**内容**
- 企业治理的常规做法也是如此：审计日志记录「谁在什么时候做了什么」，不记录数据本身

**能看**：群名、主题、人数、创建时间、最后活动时间、创建者、可见性
**不能看**：消息正文、成员名单（除非他本来就是该群成员）、文件

### 数据来源

**几乎都有了**，不需要新存储：

| 指标 | 现有来源 |
|---|---|
| 群列表、人数、最后活动 | `store.listDirectory()` 已返回 |
| 创建者 | `group.ownerPersonId` |
| 创建时间 | `group.createdAt` |
| 可见性、归档状态 | `group.settings.visibility` / `.archived` |

**缺少的只有一个**：跨群聚合（「某人建了多少群」）。这是 `state.groups` 的一次遍历，不需要新表。

### 为什么现在不做

1. **MVP 的场景是「同事协作」**，管理员视角是第二个场景，值得单独设计
2. 没有真实的管理员用户，设计出来一定偏离实际
3. 数据都齐了，什么时候做成本都一样

### 做的时候要注意

- 入口不能放在普通用户的左侧栏 —— 那会让人以为每个用户都能管
- 权限模型要先定：谁能当管理员？令牌？网关 ACL？
- 面板要能导出（管理员通常要贴到周报里）

## 2. 跨会话的群可见性收敛

**状态**：设计问题，不实现
**提出时间**：2026-11-04

### 现状

群绑定到 Session（`membership.sessionId`），但**面板快照是全局注入的**：A 会话加入的群，它的摘要也会出现在 B 会话的页面 HTML 里。

### 为什么这是个问题

绑定到会话的意义就是「这个会话的群是这些」。既然是全局快照，绑定带来的隔离只体现在 UI 过滤上，数据仍然在 HTML 里。

### 为什么现在不做

要真隔离，得改注入机制：`webserver/index-inject` 阶段没有会话上下文，得改成按会话注入或者由前端带 sessionId 拉取。

**成本不小，收益在单用户单会话时不明显。** 等有人真的在多会话间切换、且群内容敏感度不同时再做。

### 做的时候要考虑

- 前端按 `sessionId` 过滤只是 UI 层，数据还在 HTML 里 —— 不算真隔离
- 真做法：`__DSH_A2A_GROUPS__` 变成「只含当前会话的群」，需要注入时知道是哪个会话

## 3. AI 组队：按同事画像推荐团队成员

**状态**：待设计，不实现
**提出时间**：2026-11-04

### 要解决什么

建群之后，「该拉谁进来」是个真实问题。「帮我找 2 个懂后端的人」比让用户自己翻名片列表自然得多。

### 需要的形态

```
用户：帮我找两个懂后端的人加入这个群
   ↓
AI 读同事名片（persons 表：headline + tags）
   ↓
推荐 3 个候选 + 理由
   ↓
用户确认 → 逐个 a2a_person_send 邀请
```

### 为什么现在不做

**名片的信息密度不够。** 现在每个名片只有：名字、一句话简介、几个标签。按标签匹配谁都会做，不需要 AI。

有价值的推荐需要更多信号：

- 他参与过哪些群、在里面扮演什么角色（历史）
- 他现在在几个群里（忙不忙）
- 他上次活跃是什么时候

**这些都是可以采集的，但需要先有真实的群活动数据。** 现在采集，得到的是测试数据。

### 两个设计选择留待决定

**推荐由谁做**

- **A**：skill 只返回候选数据，**会话里的模型**做判断（推荐）
- **B**：skill 内部调模型

A 更简单，符合「AI 通过名片推荐」的说法，也不需要给宿主接 LLM。

**入口在哪**

- 群里说「帮我找 X」（自然，但要模型理解）
- 面板按钮（明确，但要多做 UI）

### 做的时候要注意

- 推荐理由是给人看的，必须说清「为什么是他」（「李四在三个群做过对账」比「标签匹配」有说服力）
- 已经在群里的人不该出现在候选里
- 推荐是建议不是决定，**必须等人确认才发邀请**

## 4. 网关注册自助化

**状态**：受上游限制，不实现
**提出时间**：2026-11-04

### 现状

新成员加入不需要改网关（因为成员不注册，只出站连宿主）。但**新增一个群宿主**仍然要改 `resources.yaml` 并发 SIGHUP。

### 已经验证过的限制

AISIX 的 admin API **是只读的**：
- `GET /admin/v1/a2a_agents` → 200（能读全部注册）
- `POST/PUT/PATCH/DELETE` 同一路径 → **405 Method Not Allowed**
- `POST /admin/v1/reload` 之类的 → 404

所以「让同事自己注册」在 AISIX 上做不到，不是配置问题，是它没实现写端点。

### 可能的出路

1. **换网关**，或改 AISIX 源码加写端点 —— 成本高
2. **接受人工步骤**：改 YAML + SIGHUP（热重载，不重启容器，实测 `Up 3 hours, restarts=0`）
3. **重新审视是否真的需要更多宿主** —— 一台宿主承载所有群，第二台宿主只有在「跨部门隔离」或「异地容灾」时才需要

### 为什么现在不做

**当前只有一台宿主，这个痛点不存在。** 等真有第二台时再解决，那时也更清楚约束条件。

## 5. 一对一消息的持续会话

**状态**：明确不做（当前范围外）
**提出时间**：2026-11-04

### 现在的设计

一对一消息只有三种类型：`group-invite`、`join-notice`、`welcome`。它是**门铃**，不是聊天。

### 为什么不做成聊天

用户的原话是「第一次的消息只做拉群的邀请，入群的提示就行，不需要做持续私聊，私聊请切换到建群拉人模式」。

这个判断的理由很实在：**群消息有第三个人看到上下文，有历史，@ 有语义，关机也能补收。** 私聊这些全丢。

技术上通道已经在了（`person/send` + `person/inbox` + ACK 机制），真要扩成聊天，数据模型加一个字段、去掉类型限制即可。**但那是产品决定，不是技术决定。**

### 做的前提

先有一个必须私聊、不能在群里说的真实场景。目前想不出来。

### 6.1 协作群面板两处失效

**状态**：已登记，待修（随下一版）
**登记时间**：2026-11-07
**等级**：P1 —— 不阻塞消息收发；阻塞「从面板刷新成员」「读面板设置」两条路径
**归属**：客户端面板侧。服务端 0.1.25 与 19 个群数据均正常，可排除服务端
**报告**：赵雷

#### 现象

```
① 群成员面板：刷新失败「通道没有响应」——名单只能走缓存
② 面板底部：读取设置失败
   transport failure for /a2a-panel/confirm-settings: HTTP 405
```

#### 复现

```
升级 0.1.25 → 打开协作群面板 → 点刷新成员 / 读设置
先做「完全退出重开 + 清缓存」以排除时序问题（不是 reload）
需覆盖两条路径：升级不重启 / 重启后
```

#### 已完成的定位（2026-11-07）

排除了三条错误方向：

| 排除 | 证据 |
|---|---|
| 不是 0.1.25 引入 | `git diff v0.1.24 v0.1.25`：`client.js` 与 `lib/index.js` 一行未改 |
| `/a2a-panel` 不是宿主 HTTP 路由 | `lib/core/server.js` 0 命中；`lib/index.js` 6 命中；宿主启动 routes 无此路径。它是 DSH 的 RPC 通道 |
| 不是「客户端走了 HTTP fallback」 | `client.js:1816` 的 `panelRpcCaller` 只有 `connection.rpc.call` 一条路径，无 fetch、无降级 |

**结论收窄**：`/a2a-panel` 通道没接上，请求被当未知路径回 405。注册走的是
`connection.rpc.handle(channel, handler)`（DSH 的 connection 服务），**不是 `ctx.webserver.rpc`**
（早先误记，已纠正）。

#### 下一步：日志四选一

`console.error` 共 **3 行**，加上「三行都没有」构成 **4 种状态**——四种对应四条不同修法：

| 日志 | 结论 | 修法 |
|---|---|---|
| `[a2a-panel] registered /a2a-panel` | 注册成功 | 问题在 rpc 传输层，轮到 DSH 侧 |
| `[a2a-panel] register failed: <reason>` | 注册抛异常 | reason 即根因，照改 |
| `[a2a-panel] no connection.rpc available` | `ctx.get("connection")` 拿不到 | 查 DSH 的 connection 注入契约 |
| 三行都没有 | 插件未 mount | profile / 加载问题，另一条线 |

**关于第三种**：`lib/index.js:986-990` 有一段上游 bug 记录（#8414）——

```js
// The upstream bug (#8414): registration from a plugin fiber throws
// "cannot get property webServer without inject" because the registration
// effect runs on a fiber that lacks the declaration.
// The discussion notes the ROOT context registers fine, so try the
// plugin's root before giving up.
const rootCtx = ctx.root ?? (typeof ctx.get === "function" ? ctx.get("root") : undefined) ?? ctx;
```

插件作者早已踩过并加了 `ctx.root` 兜底。若新版 DSH 改了 `ctx.root` / `ctx.get("connection")`
的语义，兜底会失效并落到这一行——**这是「代码零改动却升级后坏」的一种机制解释**。

#### 但前提尚未确认（2026-11-07，关键待办）

```
本次升级的是插件（0.1.24→0.1.25），client.js 与 lib/index.js 字节相同。
若 DSH 版本未变，则「运行时契约变了」不成立，
更可能是这个面板一直坏，只是此前没人点过「刷新成员」。
```

**先答两个问题，比查日志更快：**
1. 报告者（赵雷）的 DSH 版本是多少？0.1.24 时点过刷新成员吗？正常过吗？
2. 同一插件同 profile 的另一台机器（苏虎虎）重启后，面板能刷新成员吗？

若答案为「0.1.24 时没点过」，则 §6.1 的前提应改为「一直坏，0.1.25 才被发现」——
两个结论的修法完全不同。

**在这个对照结果出来之前不动代码。**

#### 验收标准

```
□ 刷新成功，成员名单不再只靠缓存
□ 设置可读可写
□ 覆盖「升级不重启」与「重启后」两条路径
□ 错误文案改造：不得直出 405 / 「通道没有响应」
   用户侧应读作「面板暂时连不上正在运行的会话，稍后重试或重启应用」
```

#### 证据

`03code/待修复-协作群面板刷新失败-2026-11-07/`（问题记录.md + 截图），由赵雷维护。

### 6.2 面板不显示群目标与约定（功能缺口，不是缺陷）

**状态**：已登记，待排期
**登记时间**：2026-11-07
**等级**：P1 —— 组织形态已上线，但真人从面板看不到它
**归属**：客户端面板侧 + 宿主数据发布侧

#### 现象

0.1.25 给群加了「主目标 / 群约定」，**agent 通过工具能看到，真人打开协作群面板看不到**：

```
client.js（4750 行）搜 goal / conventions / 目标 / 约定  →  0 命中
lib/index.js 的 publishGroups() 组装面板数据  →  没有把 goal 传进去
```

#### 为什么重要

组织层的目的就是「让人围绕同一个目标协作」。如果只有 agent 看得到目标、人看不到，
那这套机制就退化成了 agent 之间的私有约定——**人仍然只能借 agent 的嘴看**。

#### 修法（两条，建议都做）

```
A. publishGroups() 带上 goal 与 settings.conventions
B. client.js 渲染：群详情里显示「当前目标 + 关键路径 + 约定」
```

#### 验收标准

```
□ 打开协作群 → 群详情 → 直接看到当前主目标、KR 列表、群约定
□ 没有目标的群不显示空区块（与「未启用的群零影响」同一原则）
□ 与 6.1 分开验收：修好 6.1 不会让这个自动出现
```
