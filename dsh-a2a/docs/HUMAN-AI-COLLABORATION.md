# 人和 AI 协同写代码：一次真实项目的复盘

> 素材全部来自本项目的真实开发过程：从 0.1.2 到 0.1.7，673 个自动化测试，修掉十几个 bug。
>
> 写给 FDE（非研发背景、用 AI 交付项目的人）。
>
> **核心结论**：AI 能写出能跑的代码，也能写出全绿的测试。但**它不会自己怀疑自己**。
> 人最不可替代的动作，是提供「地面上真实发生了什么」。

---

## 一、六个盲区，每个都有真实证据

### 盲区 1：用自己期待的形态去验证，永远测不出问题

**现象**：修「凭证失效」时，单元测试全绿了两轮，功能其实从没生效过。

**原因**：测试里的假对象这样抛错——

```js
const error = new Error(code);
error.code = code;          // 本地调用是这个形状
```

而真实的远程错误形状完全不同：

```js
{
  code: -32004,             // JSON-RPC 数字
  data: "not_member"        // 业务子码藏在这里
}
```

代码检查的是 `error.code === 'not_member'`，**永远不成立**。

**AI 的说明**（当时的原话）：「fake 抛你期待的形态，就永远发现不了真实形态不一样。」

**人的作用**：不介入时，这类问题会一直存在——因为**测试和实现共享同一个错误假设**。

---

### 盲区 2：只验证「代码写了」，不验证「用户能不能做到」

**现象**：面板上的「用同一个身份加入」按钮，点击后往输入框填了一句话。AI 判定为成功。

**人的一句话**：

> 「你尝试点一下这个按钮，然后观察一下输入是否能达到既定的效果。」

**执行结果**：

```
填入:  用 a2a_group_join 重新加入「发票与对账平台」（…不需要邀请链接）
执行:  ❌ invite_invalid —— 缺少邀请令牌：入群需要凭群主给你的邀请链接
```

**按钮指向了一条后端会拒绝的路。** 面板看起来对，后端看起来对，中间那条路是断的。

**这一类 bug，读代码永远发现不了。**

---

### 盲区 3：用两小时前的判断继续推理

**现象**：连续三次「还是失败」，测的都是没重启的旧进程。

```
源码改动时间:  15:13
进程启动时间:  11:39      ← 差 2 小时
```

于是「改完还是不行」这个结论，**测的是历史代码**。

**更严重的后果**：AI 会基于这个假结论，去修一个不存在的问题。

**人的作用**：这类问题要靠制度（改完必须重启）而不是靠 AI 自觉。

---

### 盲区 4：破坏被测试的对象本身

**现象**：为了造测试场景，直接改数据库、改账本、反复触发加入流程。

**结果**：一个实例的三条凭证**全部作废**——因为每次加入都会重新签发密钥，而 AI 在**真实账本**上反复探测。

**AI 自己的记录**：

> 「测试把被测状态改坏了，然后继续拿坏状态去验证。」

**这是第二次犯同样的错**（前一次是手改工作区注册表）。

**为什么难避免**：造场景最快的方式就是改数据，而改数据会污染结论。

---

### 盲区 5：同一种 bug 出现 7 次，每次都像新 bug

**现象**：同一个根因，7 种完全不同的症状。

```
字段被「白名单 mapper」丢掉
  → 读出来是 undefined
  → 看起来像「这个功能不适用」
```

7 次的表现：

| 次数 | 表面症状 |
|---|---|
| 1 | 缓存过期警告从不显示 |
| 2 | 在线状态显示错误 |
| 3 | 消息线程信息丢失 |
| 4 | 成员数显示 0 |
| 5 | 面板刷新无效 |
| 6 | 版本号不显示 |
| 7 | 接手入口不出现 |

**每一次都要花半天，因为症状完全不同。**

**没有人指出这一点时，AI 会一次次单独修，永远不知道是同一个病。**

**后来做的**：写了一个**结构性测试**，从数据源推导字段集合，断言每一层都转发。加字段时会直接变红。

> 行为测试抓不到这类 bug——它必须知道该查哪个字段，而问题恰恰是**没人记得住要加字段**。

---

### 盲区 6：症状消失 ≠ 问题解决（最危险的一条）

**现象**：某个工具报错

```
404 unknown A2A agent: agent-person-dev3
```

**AI 的第一反应**：去网关把这个 agent 注册上。改完 404 就没了。

**人的一句话**：

> 「等一下，agent-person-* 什么的，我们现在还需要吗？」

**查下去发现**：成员实例**不托管任何群**，问它要群目录本来就是错的。

真正的修法是——**问宿主，不问自己**。

**如果没有这句话**：配置改完、报错消失、bug 永久留下。而且下次换个实例，同样的错会再来一次。

## 二、人在这其中做了什么

| 人的介入 | 作用 | AI 为什么做不到 |
|---|---|---|
| **「点一下按钮试试」** | 把「界面看起来对」推进到「用户真能做到」 | AI 不会主动怀疑自己的验证方式 |
| **「操作时看不到，刷新后才对」** | 直接指出刷新机制的问题 | AI 在验证「改完 → 重启 → 打开看」 |
| **「换个方法」** | 中止了 5 轮错误猜测 | AI 会沿着错的思路一直走 |
| **「你的测试方法有问题」** | 指出验证方式本身不可信 | 这是最深的一条 |
| **「这个还需要吗」** | 阻止了一次「让症状消失」的假修复 | AI 倾向于最快消除报错 |
| **「30 秒，不要 10 分钟」** | 定义什么叫「足够好」 | 这是产品判断，不是技术判断 |
| **「用真实工作目录风险太大」** | 识别了 AI 不承担的风险 | AI 不承担后果 |

### 提炼成三条

#### ① 人提供「地面真相」

AI 的输入是**代码和日志**，人的输入是**真实同事会怎么用**。

> 「我发消息给李四，做了一次测试，你看一下双方的会话信息。」

这句话 AI 自己想不到——它会去跑单元测试。

#### ② 人负责判断「停」和「换」

```
第 1 轮：读日志 → 猜 → 错
第 2 轮：读日志 → 猜 → 错
第 3 轮：读日志 → 猜 → 错
第 4 轮：读日志 → 猜 → 错
第 5 轮：读日志 → 猜 → 错
```

**人是第 6 轮说「换个方法」的那个。**

换成「在真实运行时里跑完整流程，逐步读返回值」——**一次就定位了**。

#### ③ 人承担「这样够不够」的判断

技术上，成员数延迟 30 秒才准也可以用。

但人会问：**「同事看到 0 人会怎么想？」**

这决定了要不要修。**这不是技术判断。**

## 三、如果人不干预，会变成什么样

### 短期（1–2 周）：一套「看起来很健康」的系统

```
✅ 673 个测试全绿
✅ 面板能打开，按钮能点
✅ 日志没有明显报错
❌ 同事第一次用就卡住
```

**测试数量和真实可靠性会脱钩**——因为测试在验证 AI 自己的假设。

### 中期（1–2 月）：同一种 bug 反复出现，越来越难查

「白名单 mapper 丢字段」那个模式出现 **7 次**，每次都花半天。

**没有人指出来，AI 会继续一个个修，永远不知道这是同一个病。**

### 长期：交付一个「通过了所有检查、但第一次真实使用就失败」的东西

**最危险的不是报错，是全绿。**

因为：

- **报错会逼人去查**
- **全绿会让人签字**

### 一条更隐蔽的退化

**AI 会不断优化「让检查通过」，而不是「让事情成立」。**

真实例子：

```
判断「要不要重绘界面」的签名里，不含「最新消息序号」
  → 数据更新了，界面不重绘
```

AI 可以去改签名让它重绘。但**真正的问题是：他把「界面有没有变」当成了「功能有没有用」**。

这个差别，**只有人盯着真实使用场景时才会暴露**。

## 四、给 FDE 的可操作清单

### 你（人）必须做的事

| 时机 | 动作 |
|---|---|
| **动手前** | 说清**谁在什么场景用什么**，不是「做个 X 功能」 |
| **AI 说完成时** | **自己按用户路径走一遍**，不要看它跑测试 |
| **连续两轮没解决** | **强制换方法**，不要让它继续猜 |
| **AI 提出「改配置消除报错」** | 问一句**「这个东西还需要吗」** |
| **验收前** | 找一个真实同事，让他独立操作 |

### 判断 AI 是否真的解决了

```
❌ "测试通过了"
❌ "我验证过了"
✅ "你点一下，看看结果对不对"
✅ "日志贴出来"
```

**要求看证据，不接受结论。**

### 三个提问模板

| 提问 | 防的是什么 |
|---|---|
| **「你怎么验证的？把过程贴出来。」** | 用旧进程、旧数据、自己的假设去验证 |
| **「这个修复会让什么症状消失？根因是什么？」** | 混淆「消除报错」和「解决问题」 |
| **「如果不是这样，还会是什么？」** | 一条路走死，不给第二解释 |

### 一句话判断「AI 是不是在瞎猜」

> **看它有没有在「读一个具体的返回值」，还是在「描述一个可能的原因」。**

- ✅「我跑了 X，返回是 Y」——在验证
- ❌「可能是因为 Z」——在猜

## 五、这次项目里，真正的进展都发生在人说话之后

| 人的话 | 之后发生了什么 |
|---|---|
| 「点一下按钮」 | 发现提示词执行不通，修了后端凭证路径 |
| 「操作时看不到」 | 发现快照是冻结的，轮询读的是死数据 |
| 「换个方法」 | 5 轮猜测结束，一次定位 |
| 「这个还需要吗」 | 避免了一次假修复 |
| 「你的测试方法有问题」 | 改成隔离环境验证，不再污染真实数据 |

## 六、给 AI 协作者的说明（也就是给 AI 看的）

如果你是被派来做这件事的 AI，请记住：

1. **报告完成之前，先问自己「我测的是新代码吗」**——比对进程启动时间和源码修改时间。
2. **不要用自己造的假对象形状去验证真实链路**——从真实调用里抄返回值。
3. **「报错消失了」不等于「问题解决了」**——说出根因，并解释为什么这个改动能消除根因。
4. **连续两次没定位，就换方法**——不要沿着同一个假设继续推。
5. **不要在生产数据上做破坏性实验**——用隔离目录。
6. **同一种 bug 出现第二次时，停下来找共同点**——写一个结构性测试，而不是修第三次。
