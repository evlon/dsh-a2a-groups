fix: a role save that changes nothing no longer announces itself

A member reported six 「张工 更新了本群角色」 lines in a feed where the description had changed twice, with
the interval shrinking from two hours to a hundred seconds. That is worse than noise: it makes the change
notification useless, because a member can no longer tell an update from a repeat — and the reporter
reasonably concluded "something is calling the write endpoint in a loop" and stopped replying to the
broadcasts.

Nothing was looping. `setProfile` wrote the system entry unconditionally, so every save announced itself
whether or not the value differed. A dialog opened and saved three times produced three announcements.

NOW

    real change    feed 18 -> 19   (+1, recorded)
    same again     feed 19 -> 19   (+0, silent)

Two details that make the comparison correct rather than approximately correct:

- **tags are normalised on both sides.** Comparing a raw array against a normalised one would report a
  change on every save — the same bug wearing a different hat.
- **`profileUpdatedAt` is not stamped on a no-op.** That field means "when this last changed", so bumping it
  would make the stored value lie in exactly the way the feed line did.

The write path also returns `changed`, so the panel can distinguish "saved" from "already that value"
instead of saying 已保存 for both.

WHY THIS TOOK A DETOUR

The store-level fix passed its own test immediately while the live feed kept growing, because the member
instance reaches the host over A2A and the HOST process is what runs `setProfile`. The plugin in 3091 looked
fixed and was irrelevant; the host needed the restart. Worth recording because the symptom — "the fix did
not work" — pointed at the wrong process.

Verified: 422 tests, store-level (`changed: true / false / true`, two system entries not three), and
end-to-end through the gateway with feed counts before and after.
