fix: `group/read` returned the author as a bare string, losing the name

A four-process walkthrough — three DSH instances and a standalone host, each on its own port and home —
surfaced this on the first full read:

    [message] : 对账这块我梳理完了，李四你看下接口定义
              ↑ the author's name is missing

THE CAUSE

The read serializer flattened `from` to its display name and hoisted `personId` alongside:

    from: entry.from.displayName,
    personId: entry.from.personId,

but `publicEntry` documents `from: { personId, displayName }`. Every consumer reading `from.displayName`
got `undefined`. It stayed hidden because the panel no longer renders message bodies (the security fix), so
nothing in the UI was reading the field.

WHY THE WALKTHROUGH FOUND IT AND THE SUITE DID NOT

The tests assert on `entry.from.personId` and on rendered panel text. Neither touches the author NAME on a
read entry — so the suite was green while a documented field was empty. Running the real flow over four
processes is what made it visible.

ALSO IN THE REPORT

The walkthrough produced `docs`-adjacent evidence: `TEST-REPORT.md` plus four screenshots covering the
owner's and both members' views. Both remaining findings are recorded there; the other one (a hardcoded home
path in the screenshot script) was a test-tool bug, now fixed.

A LESSON WORTH KEEPING

While fixing this I replaced one line by index but wrote three comment lines into the same slot, pushing
`kind` and `text` out of the object. `node --check` passed, because the result was still valid syntax. A
syntax check is not a behaviour check, and that is why the fix was verified by reading a real feed afterwards
rather than by the check alone.

Verified: 427 tests, and on the live host `from: {"displayName":"张三","personId":"m-dbf471ab"}`.
