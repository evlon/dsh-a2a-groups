refactor: personId identifies a person; add the persons table

Two changes that belong together, because the second is what makes the first true.

IDENTITY

`memberId` was minted per join, so one person in two groups was two ids. That leaked into
everything a person touches: `@` somebody by id worked in one group and not the other, and a
colleague card had to be stitched together across groups by display name.

The allocation was already globally unique — it checked every group before returning — so the
id space was right and only the reuse was missing. Now a join reuses the id the caller already
holds, which is what `@` needs and what makes "who is this" answerable across groups.

Renamed to say so: memberId → personId, memberKey → personKey, ownerMemberId → ownerPersonId,
targetMemberId → targetPersonId, allocateMemberId → allocatePersonId. 686 occurrences across 21
files, plus 213 in the probe scripts.

Deliberately NOT renamed: `group.members[]`. A membership row carries role, joinedAt and
roleAbout — facts about the RELATIONSHIP, not the person. Calling it `persons` would erase the
distinction the whole change is about.

The credential is still per-group. `resolveMember` looks the id up inside ONE group and compares
against that group's keyHash, so a key minted in A cannot authenticate in B. A stable id does not
make a key portable.

PROFILES

A `persons` table: one row per person, `{ personId, displayName, headline, tags, endpoint }`,
stored beside `groups` in the same file. Layer A (what I do in THIS group) stays on the
membership row, because it differs per group; a card now shows the group-independent profile
instead of restating which groups the reader already shares.

Old data is cleared rather than migrated, by decision: a `personId ?? memberId` read path would
live in the repository forever to serve files nobody keeps.

One bug worth recording: the first version of the reuse rejected a preferred id that was already
taken — but a person's own id IS already taken, by their first group. Every new group minted a
second identity for the same human. The check now honours the id unconditionally, keeping only a
shape test so a foreign id cannot enter this store.

Verification: 359 tests, MCP probe OK, standalone host OK, and end to end over A2A — same
personId across two groups, @ by personId resolves, rename/remove/archive all work, history
survives removal.
