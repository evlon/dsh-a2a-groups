feat: a join now tells both sides

`person/send` has carried `join-notice` and `welcome` since it was written, and nothing ever sent one. So a
join produced a line in the feed that the owner sees only if they happen to be looking, and the newcomer got
no statement of what they had walked into — the invitation flow was one-directional.

    owner      [join-notice] 李四 加入了「入群提示验证」
    newcomer   [welcome]     欢迎加入「入群提示验证」

Both verified against a live host, and both reported in the join result (`notifiedOwner`, `welcomed`) so
"did the owner get told?" is answerable instead of assumed.

THE WELCOME CANNOT BE SIGNED BY THE PERSON BEING WELCOMED

The store refuses a message from yourself, which is not an inconvenience here but the right rule: a greeting
signed by its own recipient reads oddly and gives the UI a sender it has to special-case. The owner signs it;
a group with no owner gets a reserved `system` id — deliberately not a session id, because pretending a
session identifier is a person id is how ids stop meaning one thing.

NEITHER MESSAGE CARRIES THE INVITE TOKEN

A notice that quoted the invitation would put the token in the owner's own inbox, which is precisely where a
forwarded screenshot comes from. Asserted, because it is the kind of leak that looks helpful.

A FAILURE TO NOTIFY DOES NOT FAIL THE JOIN

The membership is already on disk. A missing courtesy costs nothing; turning it into an error would report a
failed join for somebody who is, in fact, in the group.

Verified: 427 tests (5 new — both directions, self-send refusal, no token in the payload, owner not notified
about their own join, and notice surviving an absent owner), plus the live run above.
