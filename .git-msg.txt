fix: an invite link that looks like an address, not like machine noise

A colleague receives this unsolicited, in WeChat or Feishu, and has to decide whether to paste it
into their terminal:

    before  agent-a2a://group?v=1&gw=http%3A%2F%2F127.0.0.1%3A3000%2Fa2a&agent=...
    after   agent-a2a://group?v=1&gw=http://127.0.0.1:3000/a2a&agent=...

`%3A%2F%2F` is `://`. `URLSearchParams` escapes every reserved character it knows, including ones
that are perfectly legal unescaped inside a query value. The result looks like an exploit, arriving
from a colleague, asking to be trusted — and a reasonable person hesitating over it is the bug,
because the link is legitimate.

Only the escaping changed. The link format, the field order and the parser are untouched: `:` `/`
`@` are legal in a query value per RFC 3986, and `URLSearchParams.get` decodes both spellings to the
same string, so the readable form parses back to identical fields.

Non-ASCII stays escaped. That is the line: a Chinese group name cannot appear raw in a URI, and
unescaping it would produce a link some clients silently truncate. The reduction stops where
correctness starts.

I considered dropping `gw` from the link entirely, since the receiver usually has its own gateway
configured. Rejected: the link is the only thing a new colleague has, and making it depend on prior
configuration defeats the one step it exists to remove.

Verified: 408 tests (5 new, covering the readable form, the @ case, the escaped-Chinese boundary,
exact round-trip, and unchanged field order), and the live invite message now reads
`gw=http://127.0.0.1:3000/a2a`.
