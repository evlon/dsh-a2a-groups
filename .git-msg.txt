fix(ui): the dialog was dark-on-dark because the theme variables do not exist

`background: var(--dsh-color-bg-elevated, #1c2027)` — that variable is not defined in this theme, so the
fallback applied while the text stayed inherited black. On a light background that is dark grey on
near-black: exactly the unreadable result that got reported.

Checking the live page found something worse than one bad colour: **28 occurrences of five
`--dsh-color-*` variables across this file, and none of them exist.** The real variables are
per-widget (`--dsh-boot-bg`, `--dsh-frame-chrome-top`, `--dsh-scrollbar-thumb`…), with no general
background/text/border set to plug into. So every one of those has been rendering its fallback hex all
along. It looked fine only because the fallbacks happened to suit a dark theme; the dialog broke because
it needed an actual SURFACE and its fallback was a dark one.

REPLACED WITH THINGS THAT FOLLOW THE THEME

- Surfaces use `Canvas`, text uses `CanvasText` — CSS system colours that resolve to the current
  theme's window colours without this file knowing which theme is active. Plus `colorScheme: "light
  dark"` so form controls and scrollbars match.
- Borders become `rgba(128,128,128,0.35)`: a neutral that darkens slightly on white and lightens
  slightly on black, because it composites against the surface instead of asserting one.
- Icons and secondary text inherit; the host panel already chose a legible colour for its surface.
- Emphasis (accent) uses `currentColor` rather than a hue: a blue that reads on white vanishes on dark
  and vice versa, so importance is carried by contrast against dimmed neighbours instead.
- The presence dot keeps a fixed `#3fb950`, the one place a hue is right — success green is not
  theme-dependent.

Verified: 0 stale references left, 422 tests, and the live dialog measures
`background rgb(255,255,255)` / `color rgb(0,0,0)` for the panel, its input, and its list items.
