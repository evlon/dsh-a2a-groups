fix: a group created through MCP could not be invited to

The MCP walkthrough — CodeBuddy in non-interactive mode calling this server over stdio — found it on the
second real task:

    cbc -p "对群 g-c728b019 做两件事：生成邀请；发一条消息"

    消息已发出（seq 2）。但邀请没有生成：
    "g-c728b019" is hosted elsewhere; only this instance's own groups can be administered here

`a2a_group_create` accepts an `agent` and creates the group on a remote host, which is the NORMAL case
(the host is a standalone server). But `a2a_group_invite` gated on `local === true`. So a client could
create a group it could not invite anybody to — and MCP always hits this path, because an MCP client has
no hosted groups of its own.

WHY THE HOST MUST MINT

The invite token is stored (hashed) on the host that owns the group. Only that process can create a link
the same process will accept, so `a2a_group_invite` now branches: in-process for a local group, and over
`bridge.send` to `group/invite` for a remote one. The caller sends its own owner credential and the host
verifies it — this instance never gains authority it does not have.

       有效期到 2026-11-11T09:09:29Z

ALSO ESTABLISHED

MCP exposes all 25 tools with complete schemas — verified by a raw stdio handshake, not only through the
model — and `cbc` drives them: it created `g-c728b019`, read it back with the right name and owner role,
and posted to it. Reports live in `.shots/mcp/`.

Two limits are protocol, not implementation: MCP has no server push, so a client cannot be woken by a
group message and has to read on its own initiative; and it has no UI, so everything is described in
conversation.
